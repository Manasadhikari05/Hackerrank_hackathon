# Evaluation Report — Ghost Data Still Exists deletion-audit agent

## 1. How the system is evaluated

The workflow is one command, `python3 code/evaluation/main.py --tests --full --write-report`. It runs
the same checks that CI (`.github/workflows/ci.yml`) runs on every push and pull request.

1. **Tests.** It runs the pytest suite: 142 tests across the unit, contract, validation (negative),
   integration/edge-case, regression and end-to-end layers. One live-LLM test is opt-in and skipped by default.
2. **Contract validation of every output.** It runs the agent on the 32 published samples, on the custom
   cases, and (`--full`) on all 518 requests. Each written CSV is checked by the reusable validators in
   `code/deletion_auditor/validation/validators.py`:
   - `OutputSchemaValidator` checks the header, row count, unique and naturally sorted `case_id`s, allowed
     statuses, valid JSON arrays, the exact 7 step keys, and that each operation is allowed and matches its phase and state.
   - `StepOrderValidator` checks that steps are numbered 1..n and ordered by phase, then operation-table
     order, then `system_id`, then `resource_id`, with no duplicates.
   - `EvidenceReferenceValidator` checks that findings and COMPLETE verifications cite an existing
     `file_id`, `activity_id` or `audit_id` whose manifest/event time is at or before `audit_at`, and that
     remediation and future verification steps use `""`.
   - `DecisionInvariantValidator` checks that:
     - NOT_APPLICABLE rows have `[]`;
     - COMPLETE rows contain only verification steps, **and at least one** (a COMPLETE must prove something);
     - in INCOMPLETE rows every finding has a remediation, every remediation has a supporting finding, and
       every remediation has a verification.

     At model level it also checks that no case is COMPLETE while an assessed record is non-compliant or
     unproven, and that an INCOMPLETE with no violation is explicitly flagged as insufficient evidence.

   Any violation raises `OutputValidationError` and the run exits non-zero. Nothing is accepted silently.
3. **Comparison with permitted reference answers.** The agent's output is compared with
   `dataset/sample_output.csv` and with `code/evaluation/custom_cases/expected_output.csv`, which I wrote by hand.
4. **Quality gates.** The run fails if any of these holds:
   - the agent claims COMPLETE on a sample whose reference is not COMPLETE (**zero false COMPLETEs**);
   - any sample status mismatch is something other than an insufficient-evidence INCOMPLETE (no finding,
     no remediation);
   - sample step precision is below 95%;
   - sample status accuracy is below 90%;
   - custom-case sequence accuracy is below 100%.

   The status floor was 95% before the compliance audit. Section 4 (A1) explains why it changed, and the
   two structural gates above it are new and strictly tighter.

### Metric definitions

| Metric | Definition |
|---|---|
| Case-level status accuracy | Share of cases whose `deletion_status` equals the reference |
| Step precision / recall / F1 (key) | Multiset match of steps on `(operation, system_id, resource_id)` |
| Step precision / recall / F1 (exact) | Multiset match on every field except `step_no` (so `phase`, `state` and `evidence_id` must all match) |
| Field accuracy | For steps matched on key: share whose `phase`, `state`, `evidence_id` and `step_no` equal the reference |
| Sequence accuracy | Share of cases whose whole `steps_json` array is identical, including order and numbering |

### Reading the sample results

- **Precision is the safety-critical number.** Every step the agent emits on the samples appears in the
  reference answer. A false finding would ask an operator to delete or redact the wrong customer's data.
- **No false COMPLETE.** All three status mismatches (`case_01`, `case_02`, `case_04`) are cases the
  reference marks COMPLETE but where no participant-visible evidence available at `audit_at` links any
  record to the subject. Previously the agent emitted COMPLETE with `[]` for these, which is an unproven
  claim. It now emits INCOMPLETE `[]` (insufficient evidence), by design.
- **Recall is limited by the evidence, not the logic.** Every remaining missed step is one of three kinds:
  - **Resources with no identifier link anywhere in participant evidence.** For example `account_001` and
    `account_5521` appear only as `DELETE_RECORD` claims in `system_activity.csv`, batched with other
    customers' accounts.
  - **Anonymized analytics profiles** whose identifier fields are all null.
  - **Resources whose only linking or state evidence is in an evidence item captured after `audit_at`.**
    These are excluded on purpose (fix A3).

  Linking the first two kinds would require guessing among customers processed in the same batch. I chose
  not to guess, because a wrong guess costs a false positive and still misses the true step.
- **Sequence accuracy** is low for the same reason: one missing step shifts every later `step_no`. Phase,
  state and evidence fields of matched steps are all correct.

## 5. Known limitations

- **Unlinkable resources.** See section 2. About 18% of reference steps on the samples refer to resources
  with no identifier link in evidence available at `audit_at`.
- **Insufficient-evidence rows.** On the samples, 3 cases the reference marks COMPLETE are INCOMPLETE `[]`
  because no identifier in evidence available at `audit_at` links their records (R1). In the full run no
  INCOMPLETE row is empty: `case_55` carries only the policy-required `VERIFY_RESTORE_BLOCKED` check.
- **Screenshot panels.** The detail-panel crop box is measured on the supplied console layouts. A screen
  without that layout falls back to whole-page OCR, which records presence but not state.
- **Legal-hold register.** The legal-hold PDF lists order numbers, not resource ids, so it produces no records.
- **OCR quality.** OCR on screenshots is Tesseract-based. The data-catalog `LINK_RESOURCE_IDENTITY` rows
  provide an independent cross-check for every screenshot subject.
