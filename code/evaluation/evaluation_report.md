# Evaluation Report — Ghost Data Still Exists deletion-audit agent

## 1. How the system is evaluated

The workflow is one command, `python3 code/evaluation/main.py --tests --full --write-report`. It runs
the same checks that CI (`.github/workflows/ci.yml`) runs on every push and pull request.

1. **Tests.** It runs the pytest suite: 116 tests across the unit, contract, validation (negative),
   integration/edge-case, regression and end-to-end layers. One live-LLM test is opt-in and skipped by default.
2. **Contract validation of every output.** It runs the agent on the 32 published samples, on the custom
   cases, and (`--full`) on all 518 requests. Each written CSV is checked by the reusable validators in
   `code/deletion_auditor/validation/validators.py`:
   - `OutputSchemaValidator` checks the header, row count, unique and naturally sorted `case_id`s, allowed
     statuses, valid JSON arrays, the exact 7 step keys, and that each operation is allowed and matches its phase and state.
   - `StepOrderValidator` checks that steps are numbered 1..n and ordered by phase, then operation-table
     order, then `system_id`, then `resource_id`, with no duplicates.
   - `EvidenceReferenceValidator` checks that findings and COMPLETE verifications cite an existing
     `file_id`, `activity_id` or `audit_id` that was available at or before `audit_at`, and that remediation
     and future verification steps use `""`.
   - `DecisionInvariantValidator` checks that NOT_APPLICABLE rows have `[]`, COMPLETE rows contain
     verification steps only, every INCOMPLETE row has at least one finding, every finding has a remediation,
     and every remediation has a verification. At model level, no case can be COMPLETE while an assessed
     record is non-compliant.

   Any violation raises `OutputValidationError` and the run exits non-zero. Nothing is accepted silently.
3. **Comparison with permitted reference answers.** The agent's output is compared with
   `dataset/sample_output.csv` and with `code/evaluation/custom_cases/expected_output.csv`, which I wrote by hand.
4. **Quality gates.** The run fails if sample status accuracy is below 95%, sample step precision is below
   95%, or custom-case sequence accuracy is below 100%.

### Metric definitions

| Metric | Definition |
|---|---|
| Case-level status accuracy | Share of cases whose `deletion_status` equals the reference |
| Step precision / recall / F1 (key) | Multiset match of steps on `(operation, system_id, resource_id)` |
| Step precision / recall / F1 (exact) | Multiset match on every field except `step_no` (so `phase`, `state` and `evidence_id` must all match) |
| Field accuracy | For steps matched on key: share whose `phase`, `state`, `evidence_id` and `step_no` equal the reference |
| Sequence accuracy | Share of cases whose whole `steps_json` array is identical, including order and numbering |

### Reading the sample results

- **Precision is the safety-critical number.** Every step the agent emits on the samples appears in the
  reference answer. A false finding would ask an operator to delete or redact the wrong customer's data.
- **Recall is limited by the evidence, not the logic.** Every remaining missed step is one of two kinds:
  - An account resource (for example `account_001`, `account_5521`) or a security audit record that does
    not occur in any participant-visible evidence file with an identifier. It appears only as a
    `DELETE_RECORD`/`SUBMITTED` claim in `system_activity.csv`, batched together with other customers'
    accounts.
  - An anonymized analytics profile whose every identifier field is null.

  Linking either kind to a subject would require guessing among several customers processed in the same
  batch. I chose not to guess, because a wrong guess costs one false positive and still misses the true step.
- **Sequence accuracy** is low for the same reason: one missing step shifts every later `step_no`. Phase,
  state and evidence fields of matched steps are all correct.

The integration tests also run edge cases on a writable copy of this dataset:
- a deleted evidence file (skipped and counted, not fatal);
- an unsupported `.xlsx` evidence item;
- corrupt JSON;
- a request CSV with missing columns, or with duplicate `case_id`s (both fail fast with `MalformedInputError`);
- a writer that emits invalid JSON (blocked by the validator);
- a check that two runs produce byte-identical output.

## 4. Failures found and improvements made

Metrics are on the 32 samples. "Key P/R" is step precision/recall on `(operation, system, resource)`.

| # | Failure found (how) | Root cause | Fix | Effect |
|---|---|---|---|---|
| 0 | Baseline | — | First end-to-end version | Status 87.5%, key P 0.951, R 0.710 |
| 1 | `case_25` and `case_26` were classified NOT_APPLICABLE (regression diff) | "Confirm the profile is gone" and "has it been removed?" are requests to verify a deletion, but they contained no deletion keyword | Added verification-of-deletion phrases. Explicit refusals ("do not close", "not asking for deletion") still take precedence | 2 statuses fixed |
| 2 | Security audit records and log observations were missing (per-resource timeline dump) | Admissibility was decided by the export file's capture time. A log exported on 09-18 still records a lookup made on 09-16, and bundles embed sections captured earlier | Split two questions. **State** uses observations with `observed_at <= audit_at`. **Citation** requires capture `<= audit_at` | Recall up |
| 3 | `support_002` was redacted instead of deleted (diff) | Rule_05 (REDACT) applies only when the conversation has shared context that must be retained | Support records with message/ticket/order context are SUPPORT_MESSAGE (redact). Bare contact rows are deleted. Explicit labels in the evidence always win | Status 96.9% |
| 4 | Many false "absent" states (timeline dump) | I had inferred absence from a row missing in "primary" SQL tables, but those tables are partial extracts | Removed absence-by-omission. Only explicit 404 / `rows=0` / `NOT_FOUND` / `miss` / `available=false` counts as absence | Precision restored |
| 5 | Some records were read as absent although present | A sibling `cache_lookup result=miss` line in the same trace leaked `result=miss` into the record | Only query keys (`lookup_key`, `subject_key`, …) propagate across lines of a trace | Bug fixed |
| 6 | Tombstones looked absent | `account_status=DELETED` describes the account, not the tombstone row | `account_status` now means the row is present | `case_32` fixed |
| 7 | Log reads gave no state | `*_read_completed`, `message_pii_scan` and bracket-dialect lines (`[LEVEL] [svc] [trace] event:`) were not recognised | Added the fifth log dialect and treated completed reads/scans as proof of presence | Status 100% |
| 8 | Extra resources (`account_6523`, `tombstone_17` in `case_17`) | Records seen only months **before** the request are not part of what the deletion workflow left behind | A resource is in scope only if it has a non-link observation at or after `requested_at` | Precision 1.000 |
| 9 | `account_3866` was missed | It is linked to the subject only by a snapshot taken after `audit_at` | Ownership of a resource id is time-invariant, so linkage may use any evidence. **State** still uses only pre-audit observations | Recall 0.855 → 0.860 |

## 5. Known limitations

- **Unlinkable resources.** See section 2. About 14% of reference steps on the samples refer to resources
  with no identifier link in participant evidence.
- **Empty COMPLETE rows.** Three of the 518 requests have no admissible linked evidence at all, so they are
  emitted as COMPLETE with `[]`. The run log records a warning for each. Neither a citable verification nor
  a citable finding is possible for them.
- **Legal-hold register.** The legal-hold PDF lists order numbers, not resource ids, so it produces no records.
- **OCR quality.** OCR on screenshots is Tesseract-based. The data-catalog `LINK_RESOURCE_IDENTITY` rows
  provide an independent cross-check for every screenshot subject.
